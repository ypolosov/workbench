# Решение: установка workbench через Gum и автоматическую подготовку среды

## Проблема

На чистой машине запуск workbench требовал отдельно поставить Git и jq, найти bin и настроить PATH. Это оставляло подготовку продукта пользователю. Название "локальная база" также скрывало, что речь о его обычной папке с личными материалами.

## Решение

Мастер использует Gum и общий процесс на POSIX sh. Windows получает тонкий загрузчик PowerShell, который при необходимости скачивает переносимый Git. Пользователь выбирает существующий workbench, скачивание своей копии из Git или первый запуск; затем подтверждает подключения. Зависимости, доступ к команде, инструкции агентов и диагностика готовятся автоматически.

Повторная установка обновляет только программные каталоги и запускатели. Личная память, практика, рабочие продукты, решения и свои скиллы сохраняются. Местные правки программы объединяются через git merge-file; конфликт останавливает замену файлов, а прежние версии остаются в локальных резервных копиях.

В конце установщик открывает подготовленную оболочку: дочерний процесс не может изменить окружение уже работающего родителя. Для будущих оболочек используются пользовательское окружение Windows и отмеченные блоки Bash/Zsh. Команда doctor работает вручную и автоматически, не обращается к модели и показывает границы проверки.

## Почему

- [Gum](https://github.com/charmbracelet/gum) поставляет готовые бинарники для терминальных вопросов. Inquirer, Prompts и Python-библиотеки добавили бы среду исполнения к первому запуску; собственный интерфейс на Go потребовал бы отдельной сборки при сохранении ядра sh.
- По ME.8:4.1 (.fpf/Engineering DPF Suite/METHOD-ENGINEERING-PRINCIPLES-FRAMEWORK.md:2661) у запуска, выбора, подготовки и проверки есть вход, результат и условие продолжения. Запись настроек сама по себе не служит проверкой готовности.
- По SYSE.20:4.1 (.fpf/Engineering DPF Suite/SYSTEMS-ENGINEERING-PRINCIPLES-FRAMEWORK.md:8622) учитывается работа, перенесённая на пользователя. Скачивание зависимостей и настройка среды входят в установку.
- Доверие хукам записывается через API самого Codex после подтверждения пользователя; используется текущий хеш, возвращённый Codex, и только определения из подключаемых папок.
- Для переносимого Git установщик задаёт путь Git Bash для Claude Code согласно [официальной документации](https://code.claude.com/docs/en/setup#set-up-on-windows).

## Последствия

Первый запуск требует сети, а системная установка Git в Linux или macOS может потребовать подтверждения ОС. Бинарники jq, Gum и переносимого Git закреплены по версиям и SHA-256; обновление закрепления входит в сопровождение.

Проверки установки отделены от проверки аккаунта и реальной сессии агента. CI проверяет три ОС, а Windows дополнительно проходит загрузку без Git и jq в исходном PATH. Локальный прогон не заменяет результат macOS CI. Подтверждение работы модели требует доступного аккаунта и квоты.

Запись использует местный шаблон решения с минимальным составом из E.9:4 (.fpf/FPF-Spec.md:85756); это решение устройства workbench, а не изменение нормативного текста FPF.

## Условие пересмотра

Пересмотреть выбор интерфейса при отсутствии нужных бинарников Gum, нарушении доступности терминальных вопросов или необходимости сложных форм. Пересмотреть обновление при несовместимой миграции структуры личных материалов. Повторить проверки при изменении API хуков Codex, запускателей агентов или поведения оболочек.
